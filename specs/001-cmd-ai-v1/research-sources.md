### Findings
#### Base URLs, auth and the available API surfaces (high)

Direct cloud access offers three API families. Native: `https://ollama.com/api`, with POST /api/chat and GET /api/tags. OpenAI-compatible: `https://ollama.com/v1`, with /v1/chat/completions, /v1/models, /v1/completions, a stateless /v1/responses, and /v1/embeddings. Anthropic-compatible: base `https://ollama.com` plus /v1/messages. Every cloud request needs `Authorization: Bearer $OLLAMA_API_KEY`. The API 'isn't strictly versioned' but is meant to stay backward compatible. Model names on the direct API are bare names from /api/tags, such as `beam`, `gemma4:31b` and `mistral-large-3:675b`. The `:cloud` / `-cloud` suffixes (beam:cloud, gemma4:31b-cloud) are for the CLI or a local server signed in to the cloud.

**Recommendation:** config.json keeps the three fields IDEE plans: `base_url` (default `https://ollama.com/v1`, see the API-surface decision), `api_key` and `model` (default `beam`). At startup, run GET /v1/models (or /api/tags) once to check the model exists, so a retired model fails fast with a clear message. Never write the Authorization header to log/.

Sources: https://docs.ollama.com/api/introduction, https://docs.ollama.com/cloud, https://docs.ollama.com/api/authentication, https://docs.ollama.com/api/openai-compatibility, https://ollama.com/api/tags
#### Native /api/chat: request, NDJSON streaming, tool_calls and thinking (high)

Request fields: `model`, `messages`, `tools`, `think` (bool, a model-defined level string such as "low"/"medium"/"high" for gpt-oss, or null), `options` (temperature, top_p, top_k, min_p, seed, stop, num_ctx, num_predict), `stream` (default true), `keep_alive`, `format`. The response streams as `application/x-ndjson`, one JSON object per line; the last has `done:true`, `done_reason`, plus metrics `prompt_eval_count`, `prompt_eval_cached_count`, `eval_count` and durations in nanoseconds. Tool definition: {"type":"function","function":{"name","description","parameters":<JSON Schema>}}. A returned call looks like {"id":"<optional>","function":{"index":0,"name":"run_command","arguments":{...object...}}}. The result goes back as {"role":"tool","tool_name":"run_command","tool_call_id":"<id>","content":"..."}. Reasoning arrives in `message.thinking` and should be appended to history together with `tool_calls`. A mid-stream failure arrives as an NDJSON line {"error":"..."} while the HTTP status stays 200.

**Recommendation:** If native is used, read the body line by line, accumulate content, thinking and tool_calls, and treat any line that has an `error` key as a failure even on HTTP 200. Send arguments back as a JSON object, not a string.

Sources: https://docs.ollama.com/api/chat, https://docs.ollama.com/capabilities/tool-calling, https://docs.ollama.com/capabilities/thinking, https://docs.ollama.com/api/errors, https://docs.ollama.com/api/usage, https://raw.githubusercontent.com/ollama/ollama/main/api/types.go
#### OpenAI-compatible /v1/chat/completions on Ollama: what is actually mapped (high)

Supported fields: model, messages, tools, stream, stream_options.include_usage, temperature, top_p, seed, stop, max_tokens (mapped to `num_predict`), response_format, and reasoning_effort / reasoning.effort. Unsupported: tool_choice, n, logit_bias, user, logprobs; max_completion_tokens is not mapped. Streaming uses SSE: `Content-Type: text/event-stream`, each chunk sent as `data: {json}\n\n`, ending with `data: [DONE]\n\n`. With include_usage, an extra chunk carrying usage and empty choices comes just before [DONE]. Reasoning arrives as `delta.reasoning` / `message.reasoning` (not `reasoning_content`), and a `reasoning` field on an input assistant message is mapped back to Thinking. reasoning_effort mapping: "none" → think=false, "minimal" → low, low/medium/high/max accepted, "xhigh"/"ultra" → max. tool_calls[].function.arguments is a JSON string: an object returns 400 'cannot unmarshal object ... of type string', and invalid JSON returns 'invalid tool call arguments'. On tool messages, `tool_call_id` is resolved to the tool name by scanning earlier tool_calls. Usage: prompt_tokens = prompt_eval_count, completion_tokens = eval_count, and cached tokens appear in prompt_tokens_details. Errors use OpenAI shape {"error":{"message","type","param","code"}}, with type invalid_request_error (400), not_found_error (404) or api_error.

**Recommendation:** If /v1 is chosen, a hand-written SSE reader needs only about 30 lines: skip blank lines and `:` comments, strip `data: `, stop at `[DONE]`. Read reasoning from either `reasoning` or `reasoning_content` so future providers work too. Always send `stream_options:{include_usage:true}` to get exact token counts.

Sources: https://docs.ollama.com/api/openai-compatibility, https://raw.githubusercontent.com/ollama/ollama/main/openai/openai.go, https://raw.githubusercontent.com/ollama/ollama/main/middleware/openai.go, https://github.com/openclaw/openclaw/issues/96441
#### Error codes, 429 variants and retry policy (medium)

Documented status codes are 200, 400, 404, 429 (rate limit), 500 and 502 ('cloud model cannot be reached'), with body {"error":"..."}. No Retry-After header or retry guidance is documented. Observed 429 bodies fall into two kinds. Quota (legacy plans): 'you (...) have reached your session usage limit, upgrade for higher limits' plus links to ollama.com/upgrade; hourly and weekly variants also exist. Concurrency: 'timed out waiting for a concurrent request slot' after a server-side queue wait of about 5 minutes (ollama/ollama#19111, opened 2026-10-18, still open; plain probes sometimes got no HTTP response at all). There is also a client-bug 400, 'Invalid tool usage: mismatch between tool calls and tool results', which happens when an assistant `tool_calls` message is not followed by matching `tool` messages (#12395, maintainer explanation). No documented error for running out of credits.

**Recommendation:** Classify failures in the client. 429 whose body contains 'usage limit', 'upgrade' or 'credit': do not retry; show the message and point to ollama.com/settings/usage. 429 'concurrent request slot', 502 or 5xx: retry at most 2 times with backoff (for example 2 s then 8 s), then offer the fallback model. 400 'mismatch': an internal bug; repair the history before retrying. Set a connect timeout (about 15 s) and a stream-idle watchdog (60–120 s without bytes) so the 5-minute server queue cannot freeze the TUI.

Sources: https://docs.ollama.com/api/errors, https://github.com/ollama/ollama/issues/19111, https://github.com/NousResearch/hermes-agent/issues/65563, https://github.com/ollama/ollama/issues/12395

#### Beam (Reflection) specifics and early operational issues (medium)

`beam` on the direct API, `beam:cloud` in the CLI. GA on 2026-10-16, Apache 2.0, MoE with 501.3B total and 23.4B active parameters, 256 experts, 52 layers, modified Harmony chat template, knowledge cutoff 2026-06-30. 1M context, text only, tools and thinking badges, zero data retention on Ollama's endpoint. Reported benchmarks used temp=0.7 and top_p=0.99. The library page does not document how to set the thinking level. Early issues: #19270 (2026-10-24, open, a maintainer is investigating) reports intermittent empty assistant responses with 4 output tokens billed and dropped. modelparams.dev#424 (2026-10-21) reports that with ~52–78K-token prompts about 90% of the completion budget went to reasoning, leaving truncated or empty content with finish_reason 'stop'; one 52K-token request took 196 s.

**Recommendation:** Keep Beam as the default model, as IDEE intends, but harden the loop for it. Send a generous `max_tokens` (at least 16384). Try `reasoning_effort:"low"` for simple command tasks; the accepted values for Beam are unverified, so check `thinking.values` via /api/show or by trial. Keep prompts compact even though the context is 1M. Treat 'no content and no tool_calls' as a retryable failure: one retry with a short nudge, then the fallback model.

Sources: https://ollama.com/library/beam, https://ollama.com/blog/reflection-beam, https://github.com/ollama/ollama/issues/19270, https://github.com/mnfst/modelparams.dev/issues/424, https://docs.ollama.com/capabilities/thinking

The only cloud Gemma is Gemma 4 31B: `gemma4:31b` (aliases gemma4:cloud / gemma4:31b-cloud), 256K context, vision/tools/thinking/audio, $0.14 / $0.05 / $0.40 per 1M tokens. #### Free tier, plans and behaviour when limits are reached (medium)

Official page (fetched 2026-10-28): Pay as you go, $0, 'Pay per token for every cloud model', 3 concurrent requests, no subscription. Pro: $20/mo or $200/yr, $60 of monthly credits, 3 concurrent, 'larger pro models'. Max: $100/mo, $300 credits, 10 concurrent. Team: $500/mo, $1,000 shared credits, early access. Enterprise: custom, with cost budgets per user and per API key. Included credits reset monthly on the subscription day and do not roll over; plan credits are used before purchased credits; paid plans get an email at 90% usage. Requests over the concurrency limit are queued, and rejected when the queue is full. The 2026-08-31 blog dropped 5-hour and weekly limits for new plans, said the free plan keeps 'a small monthly usage amount' on starter models, and said that after credits run out you continue at per-token rates. Third-party trackers still report 'Free: 1 concurrent' as of 2026-10-19. No official per-minute rate limits are published, and no API returns remaining quota (usage is visible only at ollama.com/settings/usage).

**Recommendation:** Do not hardcode concurrency or quota numbers anywhere. Design for exactly one request in flight, which already matches IDEE's sequential model. Surface quota 429 messages verbatim. Update IDEE §2's 'Limite du free tier' line to cite the current page and its date.

Sources: https://ollama.com/pricing, https://ollama.com/blog/transparent-pricing, https://ollamatps.com/limits/, https://agentdeals.dev/vendor/ollama-cloud
#### Known tool-calling failure modes through Ollama and mitigations (medium)

Observed failures: (a) the tool-call JSON lands in `content` instead of `tool_calls`, mostly with small local models or complex prompts (hermes-agent#5867, qwen2.5-coder:14b; NemoClaw#2731). (b) Malformed string-encoded calls from glm-5.3-flash on the cloud (#18506). (c) Parallel calls sharing a function.index from mistral-large-4 (opencodex#6857). (d) 400 'mismatch between tool calls and tool results' when a call goes unanswered (#12395). (e) Argument type mismatch, string vs object, depending on the endpoint (openclaw#96441). (f) Empty responses from Beam (#19270). Ollama says cloud models trained for tools 'are tested for tool calling' before release. tool_choice is unavailable on /v1, so a tool call cannot be forced.

**Recommendation:** Mitigations for a single tool. (1) A small, flat schema of strings and booleans, with one tool. (2) A system prompt rule: 'call run_command once per turn, one command per call'. (3) If several calls still arrive, run them in array order and answer every one of them, using the call's id or a synthesized `call_<n>`. Key calls by id, then by array position, never by function.index. (4) Validate arguments; if `command` is missing or empty, return a tool error ('missing command') instead of aborting. (5) A narrow fallback parser: if `content` holds a fenced JSON or bare object with name 'run_command' and a `command` string, treat it as a tool call and log the event. (6) On empty output, retry once, then use the fallback model.

Sources: https://github.com/NousResearch/hermes-agent/issues/5867, https://github.com/NVIDIA/NemoClaw/issues/2731, https://github.com/ollama/ollama/issues/18506, https://github.com/lidge-jun/opencodex/issues/6857, https://github.com/ollama/ollama/issues/12395, https://github.com/openclaw/openclaw/issues/96441, https://github.com/ollama/ollama/issues/19270, https://ollama.com/pricing, https://docs.ollama.com/api/openai-compatibility
#### Proposed `run_command` tool schema (medium)

Prior art: Codex's `shell_command` tool takes `command` as one string plus optional `workdir`, `timeout_ms` and an escalation request. The escalation started as a `with_escalated_permissions` boolean plus a one-sentence `justification`, later replaced by `sandbox_permissions:"require_escalated"`. This comes from a third-party mirror of openai/codex and is unverified upstream. A minimal schema that fits IDEE: {"type":"function","function":{"name":"run_command","description":"Run ONE shell command on the user's machine; returns exit code, stdout, stderr (possibly truncated).","parameters":{"type":"object","properties":{"command":{"type":"string"},"shell":{"type":"string","enum":["powershell","pwsh","cmd","bash","sh","zsh"]},"purpose":{"type":"string","description":"One short sentence shown to the user"},"needs_admin":{"type":"boolean"},"plan":{"type":"array","items":{"type":"string"},"description":"Only on the first call of a task or when the plan changes: the full ordered list of steps"}},"required":["command","purpose"]}}}

**Recommendation:** Keep cwd, timeout and output limits under the app's control, not as model arguments. Default `shell` to the detected host shell and send the OS and shell in the system prompt. Treat `needs_admin` as a hint only: the app also detects elevation itself (sudo/doas prefixes, `Start-Process -Verb RunAs`, a non-elevated token on Windows) and asks before elevating. `purpose` feeds the written action line IDEE requires for every command.

Sources: https://forge.lthn.ai/core/core-agent-ide/commit/e0fb3ca1dbea0c418cf8b3c7b76ed671d62147e3, https://docs.ollama.com/capabilities/tool-calling, https://github.com/ollama/ollama/issues/18506
#### Implementing plan mode with a single tool (medium)

Constraints: 'Ollama's cloud currently does not support structured outputs', so `format` with a JSON schema cannot be used for a plan, and /v1 does not support tool_choice, so a 'plan' call cannot be forced. That leaves three options: (A) a free-text plan phase parsed with a tolerant regex, which is fragile across models; (B) the plan as a structured argument (`plan: string[]`) on the first run_command call, which Ollama's per-model tool parser returns as JSON; (C) a second 'propose_plan' tool, which breaks IDEE's one-tool principle.

**Recommendation:** Option B. In plan mode the app intercepts the first run_command call that carries `plan`. It shows the N steps (progress 0/N) and executes nothing. If the user approves, it runs the command bundled in that same call as step 1, so no extra round trip is needed. If the user rejects, it returns a tool result 'User rejected the plan: <feedback>'. The app counts executed calls to show k/N and does not trust any step index from the model. A later call with a new `plan` is a deviation and triggers re-approval in plan mode. In bypass mode the same `plan` field still drives the progress ratio.

Sources: https://docs.ollama.com/capabilities/structured-outputs, https://docs.ollama.com/api/openai-compatibility, https://docs.ollama.com/capabilities/tool-calling
#### Handling reasoning/thinking tokens in the agent loop (medium)

OpenAI's Harmony guidance for gpt-oss: while the last assistant message was a tool call, keep the earlier reasoning in history; after a `final` answer, drop the reasoning messages. The suggested Chat Completions field is `reasoning`, in both directions. Ollama follows this: on native, `message.thinking` is accumulated and sent back with tool_calls; on /v1, `reasoning` is mapped to Thinking. Beam uses a modified Harmony template, so this probably applies to it too, though that is not confirmed for Beam. Reasoning and visible output share the completion budget (modelparams.dev#424).

**Recommendation:** Keep reasoning only for the current chain of tool calls in a task and strip it from history once the model gives its final answer. Show reasoning dimmed and collapsed in the TUI; it can be written to log/. Always set max_tokens high enough for reasoning plus the answer.

Sources: https://developers.openai.com/cookbook/articles/gpt-oss/handle-raw-cot, https://docs.ollama.com/capabilities/tool-calling, https://raw.githubusercontent.com/ollama/ollama/main/openai/openai.go, https://ollama.com/library/beam, https://github.com/mnfst/modelparams.dev/issues/424
#### Lightweight token estimation without a tokenizer (medium)

Every response reports exact input and output counts: prompt_eval_count / eval_count on native, usage.prompt_tokens / completion_tokens on /v1 with include_usage. Only newly appended messages need estimating. English averages about 4 characters per token; French, code, paths and punctuation-heavy shell output come out denser. `tokenx-rs` 0.1.0 (2026-02-06, MIT, no runtime dependencies) estimates with a single pass: CJK counted as 1 token per character, punctuation runs at ceil(len/2), and a claimed ~96% accuracy against cl100k. Each cloud model has its own tokenizer, so any static estimator is approximate. How `num_ctx` behaves on cloud models is not documented (unverified), and the FAQ only describes the local default of 4096.

**Recommendation:** No tokenizer dependency. Estimate as known_tokens (from the last usage) plus new_bytes / r, starting with r = 3.0 (conservative) and recalibrating r each turn as usage.prompt_tokens divided by bytes sent. Enforce an app-level context budget well below the model maximum (for example 128K by default even on Beam's 1M) because latency and cost grow with prompt size: one 52K-token Beam request took 196 s. Do not rely on `num_ctx` for cloud models.

Sources: https://docs.ollama.com/api/usage, https://raw.githubusercontent.com/ollama/ollama/main/openai/openai.go, https://docs.rs/crate/tokenx-rs/latest, https://docs.ollama.com/faq, https://github.com/mnfst/modelparams.dev/issues/424
#### Truncating long command outputs before returning them to the model (medium)

Agent CLIs cap tool output deterministically. Codex keeps a head and a tail with a marker such as 'omitted N of M lines' or 'output truncated to fit N bytes', with byte and line limits (MODEL_FORMAT_MAX_BYTES / MODEL_FORMAT_MAX_LINES; exact values unverified, source is a mirror), while the UI still receives the full stream. Summarizing with an LLM costs an extra request against a 1–3 concurrency cap and billed tokens.

**Recommendation:** A deterministic pipeline, configurable in config.json: (1) strip ANSI/CSI escapes and carriage-return progress redraws; (2) collapse runs of identical lines ('[repeated 120×]'); (3) if the output exceeds the cap (suggested default 256 lines or 16 KiB), keep about 40% head and 60% tail with a marker giving omitted lines and bytes; (4) always prepend exit code, duration and total size; (5) write the full raw output to log/ on the stick, so the model can re-inspect it with commands (`Select-String`, `grep`, `tail`), which stays within the one-tool rule; (6) after K turns, replace old tool outputs in history with a one-line stub. No LLM summarization in V1.

Sources: https://forge.lthn.ai/core/core-agent-ide/commit/da82153a8d625c751e48e260ccf49fe34a87319d, https://forge.lthn.ai/core/core-agent-ide/commit/d7acd146fbf7626c837d64872ca8a97f3e1fb6e9, https://ollama.com/pricing
#### Minimal Rust HTTP client for the provider (high)

`ollama-rs` 0.3.6 (2026-07-24): native API only, a non-optional dependency on reqwest ^0.12.28, auth only through the `headers` feature (a raw HeaderMap), and no mention of Ollama Cloud or the /v1 endpoints. `ureq` 3.5.0 (2026-10-21; 3.4.2 dated 2026-09-13): blocking I/O with no async runtime. rustls with the ring provider and gzip are on by default; `json` is opt-in. Root certificates come from bundled webpki-roots by default, with an optional `platform-verifier` for the OS trust store. The default Agent reads ALL_PROXY, HTTPS_PROXY, HTTP_PROXY and NO_PROXY. Timeouts (timeout_connect, timeout_recv_response, timeout_recv_body, timeout_global) all default to unlimited. Bodies stream through `Body::as_reader()`.

**Recommendation:** A hand-written client of roughly 300 lines using ureq 3.x plus serde/serde_json, running on a worker thread that sends stream events to the TUI over a std mpsc channel. No tokio needed. Set the timeouts explicitly. Keep rustls with bundled roots so nothing depends on the host, and consider the `platform-verifier` toggle for TLS-intercepting networks (see risks). Do not adopt ollama-rs: it pins you to the native API and pulls in reqwest.

Sources: https://crates.io/api/v1/crates/ollama-rs, https://docs.rs/ollama-rs/0.3.6/ollama_rs/struct.Ollama.html, https://github.com/pepperoni21/ollama-rs, https://crates.io/api/v1/crates/ureq, https://docs.rs/ureq/latest/ureq/
#### Plaintext API key in config.json on a USB stick (medium)

Ollama API keys 'do not expire' and are revoked from API keys settings. Ollama allows 'one account per person', so a separate throwaway account is not an allowed mitigation. Per-API-key cost budgets exist only on Enterprise. Every plan, including $0 pay-as-you-go, can buy credits, and after included credits run out usage continues at per-token rates. A leaked key on an account with a credit balance therefore costs real money. Team can turn off automatic usage billing; no equivalent was found for individual accounts (unverified). If encryption is wanted: RustCrypto `chacha20poly1305` 0.11.0 (2026-06-28) plus `argon2` 0.6.0 (2026-08-27), both pure Rust.

**Recommendation:** Flagged as a decision, not a scope increase. For V1: plaintext key plus an `OLLAMA_API_KEY` environment-variable override, which is session-only so nothing persists on the host. Redact the key from log/ and from error output. Document in doc/ that a lost stick means revoking the key at ollama.com/settings/keys immediately. Keep the purchased credit balance small. Defer optional passphrase encryption to after V1.

Sources: https://docs.ollama.com/api/authentication, https://ollama.com/pricing, https://ollama.com/blog/transparent-pricing, https://crates.io/api/v1/crates/chacha20poly1305, https://crates.io/api/v1/crates/argon2

### Decisions
- **Which wire API should the single V1 provider adapter target?**
  - Options: OpenAI-compatible POST https://ollama.com/v1/chat/completions (SSE) | Native POST https://ollama.com/api/chat (NDJSON) | Both behind a trait from day one
  - Recommended: OpenAI-compatible POST https://ollama.com/v1/chat/completions (SSE)
  - Why: IDEE wants future OpenAI-compatible providers at low cost. One /v1 adapter makes them a config change (base_url, api_key, model). Ollama's compat layer maps everything cmd_ai needs, verified in openai.go: tools, tool_call_id, `reasoning` in both directions, reasoning_effort to think, max_tokens to num_predict, and usage. What is lost is minor: native-only `think` strings beyond the mapped levels, and NDJSON mid-stream `error` lines. Keep GET /api/tags or /v1/models for model validation. Two code-level rules: arguments are serialized as strings, and reasoning is accepted from either `reasoning` or `reasoning_content`.
- **Which HTTP stack should the Rust client use?**
  - Options: ureq 3.x + serde_json, blocking, on a worker thread | reqwest 0.12 + tokio (async) | ollama-rs 0.3.6
  - Recommended: ureq 3.x + serde_json, blocking, on a worker thread
  - Why: Lightest option that still covers streaming, rustls, gzip, proxy environment variables and explicit timeouts, with no async runtime. ollama-rs supports only the native API, documents no cloud auth, and brings reqwest in anyway.
- **How should the three IDEE model roles map to cloud tags today?**
  - Options: Primary `beam`, speed `gpt-oss:20b`, French `mistral-large-3:675b` | Primary `beam`, speed `gemma4:31b`, French `mistral-large-4` | Single model only (`beam`) for V1
  - Recommended: Primary `beam`, speed `gpt-oss:20b`, French `mistral-large-3:675b`
  - Why: Gemma 3 and Mistral Small no longer exist in the cloud. gpt-oss:20b is the cheapest small model with think levels; mistral-large-3 is the cheapest Mistral, Apache 2.0, with no thinking overhead. All non-promo models are billed per token, so the README must say credits are needed for the speed and French roles. Speed and French quality should be measured with a quick test before the spec locks them.
- **How should plan mode be implemented while keeping a single tool?**
  - Options: `plan: string[]` argument on the first run_command call, intercepted by the app | A separate text-only planning turn parsed with a regex | A second internal `propose_plan` tool
  - Recommended: `plan: string[]` argument on the first run_command call, intercepted by the app
  - Why: Cloud has no structured outputs and /v1 has no tool_choice, so the only structured channel is tool arguments, which Ollama's per-model parsers turn into JSON. It keeps one tool, adds no extra round trip (step 1 runs after approval) and gives the k/N progress ratio IDEE asks for.
- **Which arguments should run_command expose to the model?**
  - Options: command, purpose (required) + shell, needs_admin, plan (optional) | Codex-like: command, workdir, timeout_ms, sandbox_permissions, justification | command only
  - Recommended: command, purpose (required) + shell, needs_admin, plan (optional)
  - Why: Fewer and flatter arguments mean fewer malformed calls on open-weight models. `purpose` satisfies IDEE's written action line, `needs_admin` and `shell` feed the elevation and multi-shell logic, and cwd and timeouts stay deterministic on the app side.
- **How should the client react to 429 and other failures?**
  - Options: Classify by body text: quota means stop and show; concurrency/5xx/502 means bounded backoff, then fallback | Generic exponential retry on every 429 | No retries
  - Recommended: Classify by body text: quota means stop and show; concurrency/5xx/502 means bounded backoff, then fallback
  - Why: Ollama sends no Retry-After header. Quota 429s ('usage limit… upgrade') never clear by retrying, while concurrency-slot 429s and 502s are transient. A stream-idle watchdog is needed because of the 5-minute server-side queue (#19111).
- **How should the API key be stored on the USB stick?**
  - Options: Plaintext config.json + OLLAMA_API_KEY env override + log redaction + documented revocation | Passphrase-encrypted key (argon2 + chacha20poly1305) unlocked at startup | OS keychain
  - Recommended: Plaintext config.json + OLLAMA_API_KEY env override + log redaction + documented revocation
  - Why: Matches the plug-and-go scenario and the --prompt one-shot mode, where a passphrase prompt would get in the way. The OS keychain breaks the 'nothing on the host' rule. Keys never expire, so revocation steps must be documented, and keeping a small credit balance limits what a stolen key can cost. Encryption stays a possible post-V1 option.
- **How should long command outputs be reduced before going back to the model?**
  - Options: Deterministic: strip ANSI, dedupe, head+tail cap (256 lines / 16 KiB default), full output in log/ | LLM summarization of long outputs | No truncation (rely on 1M context)
  - Recommended: Deterministic: strip ANSI, dedupe, head+tail cap (256 lines / 16 KiB default), full output in log/
  - Why: No extra request against the 1–3 concurrency slots or the credit balance. It is predictable and testable as a pure function, which suits the IDEE requirement for unit tests. The model can re-inspect the logged output with further commands.
- **How should token usage be estimated?**
  - Options: Server-reported usage + calibrated bytes/ratio for new messages | tokenx-rs 0.1.0 heuristic | Real per-model tokenizers (tokenizers / tiktoken-rs)
  - Recommended: Server-reported usage + calibrated bytes/ratio for new messages
  - Why: No dependency. Exact counts come back on every response, so only the small new part is estimated, and the per-session ratio adapts to each model's tokenizer. Real tokenizers would add megabytes and still not match every cloud model.

### Risks
- [high] The Beam free promo ends without notice (no end date published), and the default model starts consuming credits or failing. — *Mitigation:* Keep the model in config, document a fallback (`gpt-oss:120b`), and validate the model at startup. Surface quota and credit 429 messages verbatim. Avoid wording in docs and README that promises Beam is free.
- [high] Ollama changes pricing or limits again (it already did on 2026-08-31, and the official page and trackers disagree today), which invalidates assumptions in the spec. — *Mitigation:* Never hardcode concurrency or quota values. Cite ollama.com/pricing with a date in doc/. Design for one request in flight.
- [medium] Beam-specific instability: intermittent empty responses (#19270) and verbose reasoning using up the output budget on large prompts (#424), with latency up to about 196 s at 52K tokens. — *Mitigation:* Set max_tokens to at least 16384, use reasoning_effort 'low' for simple tasks, enforce an app context budget and output truncation, retry once on 'no content and no tool_calls', then fall back. Use a stream-idle watchdog.
- [medium] Cloud model retirement: gemma3 and ministral-3 already retired on 2026-07-15, and a model named in the default config could disappear. — *Mitigation:* Run GET /v1/models at startup, give a clear error listing available tool-capable models, and keep model names only in config.json and the docs.
- [medium] Malformed or misplaced tool calls (in content, string-encoded, duplicate index, unanswered calls causing a 400 mismatch). — *Mitigation:* Small flat schema, key calls by id then by position, answer every call, use a narrow fallback parser for JSON in content, validate arguments and send tool errors back instead of aborting.
- [medium] Server-side queueing: requests hang about 5 minutes then return 429 'timed out waiting for a concurrent request slot', or get no HTTP response (#19111, open). — *Mitigation:* Explicit ureq timeouts (connect about 15 s), a stream-idle watchdog of 60–120 s, a cancel key in the TUI, and bounded retries.
- [medium] Lost USB stick means a leaked non-expiring API key and possible spending of purchased credits. — *Mitigation:* Document revocation (ollama.com/settings/keys), keep a minimal credit balance, offer the OLLAMA_API_KEY env override, and redact the key from log/.
- [medium] Command outputs sent to the cloud can contain host secrets (env vars, tokens, file contents) from a machine that is not the user's own. — *Mitigation:* Ollama states prompts are not logged or trained on and that Beam runs with zero data retention, hosted mainly in the US with possible routing to Europe. Still, state this in the docs and consider a simple redaction pass for obvious secrets in a later version.
- [low] Restricted networks (library, corporate) use proxies or TLS interception, so bundled webpki roots are rejected. — *Mitigation:* ureq honours HTTPS_PROXY and NO_PROXY. Expose an optional config toggle for the platform verifier (OS trust store) and give a clear TLS error message.

#### 1b. Inline viewport vs alternate screen for 'TUI ouvert' (high)

Viewport::Inline(h) anchors a live region of h rows at the cursor row. Terminal::insert_before(height, draw_fn) pushes rendered lines above it, and they flow into the terminal's native scrollback. Each executed command and its output therefore stays visible and copyable after exit, without being written to disk. That fits IDEE §3 ('on voit clairement quelles actions ont été faites') and §4 (nothing stored). Without the 'scrolling-regions' feature, insert_before clears and repaints the viewport; with it, there is no flicker. The official inline example uses std threads, mpsc and Viewport::Inline(8) with Gauge and LineGauge. An alternate screen loses all output at exit. Inline mode has known rough edges. #2640 (open, 2026-07): inline construction issues CPR queries that race stdin. #984 (open): inline viewport resize. #2666 (scrollback duplication on resize) is closed.

**Recommendation:** For 'TUI ouvert', use the inline viewport, about 6-10 rows: a status line with ratio and percentage, the current command and a tail of live output. When a command finishes, insert_before its full transcript. Never use the alternate screen. For 'TUI fermé' and whenever !stdout.is_terminal(), skip ratatui and print plain prefixed lines ('[2/4] $ cmd', output, exit code). Build ratatui::init_with_options/try_init_with_options or ratatui::run so a panic hook restores the terminal. Evaluate 'scrolling-regions' on conhost before enabling it.

#### 2. Color-level detection (truecolor/256/16/none) and NO_COLOR (high)

NO_COLOR (spec updated 2026-10-12) disables color when the variable is present and non-empty; user config and CLI flags should override it. crossterm already honors NO_COLOR at the Colored level and exposes force_color_output(bool). crossterm::style::available_color_count() returns u16::MAX on Windows when ANSI is supported. Elsewhere it checks COLORTERM, then TERM, for '24bit'/'truecolor' or '256', with a fallback of 8; its docs warn it 'does not always provide a good result'. Several tools miss WT_SESSION (Windows Terminal, also forwarded into WSL), which leads to 256-color quantization. Windows conhost has supported 24-bit color since build 14931. Apple Terminal.app supports truecolor only since macOS 26, so older Macs ('chez quelqu'un, sur un Mac') get 256 colors. Neither crossterm nor ratatui downsamples Color::Rgb; the app must pick per-level colors. Ready-made options: anstyle-query 1.1.5 (env-var probes, depends on windows-sys) and termprofile 0.2.5, which adds levels, adapt_color and ratatui integration but pulls termina, termini and ratatui-core.

**Recommendation:** Hand-roll about 40 lines of detection, ordered: config.json 'color' (auto|truecolor|256|16|none) > CLI flag > NO_COLOR non-empty → none > !is_terminal → none > COLORTERM contains truecolor/24bit, or WT_SESSION set, or Windows with VT enabled → truecolor > TERM contains 256color, or TERM_PROGRAM=Apple_Terminal → 256 > else 16. #### 2b. Perceptual palette (OKLCH/OKLab) with accessible contrast (medium)

OKLab (Ottosson, 2020) predicts perceived lightness, chroma and hue, so equal-L steps look equally bright. OKLCH is its polar form (C = √(a²+b²), h = atan2(b,a)). The conversion from linear sRGB is two 3×3 matrices and a cube root, a few lines of Rust. WCAG 2.2 SC 1.4.3 (AA) requires 4.5:1 for normal text, using (L1+0.05)/(L2+0.05). APCA (Lc 60/75/90 tiers; Lc 75 is the minimum for body text) is still a WCAG 3 draft, so it is a design-quality layer, not the compliance baseline. Small crates exist (oklab 1.1.2, last updated 2024-09), but the palette is fixed, so no runtime color math is needed.

**Recommendation:** Generate the palette offline with a tiny build-time or dev script, or in a doc page. Choose hues in OKLCH at fixed L levels (for example L≈0.72 accents for dark backgrounds and L≈0.48 for light backgrounds) and verify each against #000/#fff and typical terminal backgrounds for WCAG ≥4.5:1, with APCA Lc ≥60 as a secondary target. Emit const RGB values plus the nearest xterm-256 index and the ANSI-16 mapping. Body text and command output use Color::Reset (the terminal's own fg/bg), so contrast stays correct whatever the theme. Color is reserved for chrome: status, ratio, success/failure, admin warnings.

#### 4. Concurrency: std threads + channels, not tokio (high)

The workload is one UI loop, one LLM stream (the free tier allows 1 concurrent request) and one child process at a time with two pipes. That fits a handful of OS threads. ratatui's official inline example uses std::thread plus std::sync::mpsc with no async runtime, and the ratatui FAQ advises avoiding tokio when async buys little. std::sync::mpsc has been crossbeam-based since Rust 1.67, so crossbeam-channel adds nothing. tokio 1.54.1 (2026-10-21; 1.54.0 yanked) would come in only via reqwest, at about 2.9 MiB more than ureq in the benchmark. Child-process facts: Child has no Drop, so it keeps running unless waited on or killed. Child::kill is SIGKILL on Unix and reaches only the direct child. Unix CommandExt::process_group(0) (stable 1.64) makes a group that killpg can signal. On Windows, a Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE / TerminateJobObject terminates the whole tree.

**Recommendation:** Use one `enum AppEvent { Key, Resize, Tick, LlmToken, LlmDone, CmdStdout(line), CmdStderr(line), CmdExit(code), HookFired }` over std::sync::mpsc. Threads: (1) input, which polls crossterm events and forwards Press keys; (2) LLM, which runs a blocking ureq read loop and checks an AtomicBool cancel flag per line; (3) per command, one thread each for stdout and stderr (read both concurrently to avoid pipe deadlock) plus a waiter. The main thread owns the Terminal and redraws at most every ~33-50 ms. On cancel, kill the process tree: a Job Object on Windows via windows-sys, process_group + killpg on Unix via libc.

Sources: https://ratatui.rs/examples/apps/inline/, https://ratatui.rs/faq/, https://blog.rust-lang.org/2023/01/26/Rust-1.67.0/, https://crates.io/api/v1/crates/tokio, https://github.com/CarloTUM/rust-http-client-bench, https://doc.rust-lang.org/std/process/struct.Child.html, https://doc.rust-lang.org/std/os/unix/process/trait.CommandExt.html, https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects

#### 7. Release profile, binary size and startup (medium)

Cargo's release defaults are opt-level=3, strip='none', lto=false, codegen-units=16 and panic='unwind'. min-sized-rust's stable steps: strip=true (Rust 1.59+), opt-level='z' (sometimes 's' is smaller), lto=true (= 'fat'), codegen-units=1 and panic='abort'. The nightly-only steps are -Zlocation-detail=none, -Zfmt-debug=none and build-std with optimize_for_size. UPX packing is warned against because heuristic antivirus flags it. With panic='abort', the panic hook still runs ('the hook will run with both the aborting and unwinding runtimes'), so ratatui's terminal-restore hook works, but Drop guards do not. cargo-bloat (--release --crates, -n 10) supports ELF, Mach-O and PE. Measured anchor: ureq + rustls/ring is 1,928 KiB stripped, against a 281 KiB empty binary. An estimate for the whole stack (+ratatui/crossterm, serde_json, platform-verifier, lexopt) is about 2.5-3.5 MiB stripped. That figure is an unverified extrapolation; no ratatui size benchmark was found.

**Recommendation:** [profile.release] opt-level = "z" (benchmark against "s" once), lto = true, codegen-units = 1, panic = "abort", strip = true. Stay on stable and skip build-std and UPX. Add a CI job that runs `cargo bloat --release --crates -n 15` and fails if the stripped binary exceeds a budget (for example 4 MiB). Startup target: under 10 ms to first paint. #### 10. Hooks: config shape and file-change detection (medium)

Claude Code's shape is: hooks → { EventName: [ { matcher, hooks: [ { type: 'command', command, timeout } ] } ] }. Events include PreToolUse, PostToolUse, UserPromptSubmit, Stop, SessionStart, FileChanged and CwdChanged, among others. Input is JSON on stdin. Exit 0 parses stdout JSON; exit 2 blocks events that can block (PreToolUse yes, PostToolUse no); other codes are non-blocking errors. FileChanged uses a filesystem watcher, its matcher is a '|'-separated list of literal filenames, it receives file_path and event (change|add|unlink) and it cannot block. notify 8.2.1 (stable, 2026-10-25) and 9.0.0-rc.7 (2026-10-27) provide inotify, FSEvents (default macos_fsevent), kqueue, Windows and PollWatcher backends. Hooks run through the same shell executor, appear in the progress log, and do not count toward N/M. For V1, implement FileChanged without notify: stat the mtime and length of an explicit watch list (literal paths or the matcher's filenames in cwd) before and after every executed command, plus a 1-2 s poll only while the TUI is idle. #### 11. Skills with a single tool: format, progressive disclosure and loading (high)

In the Agent Skills spec a skill is skills/<name>/SKILL.md. Required name: 1-64 chars, lowercase alphanumerics and hyphens, matching the directory. Required description: 1-1024 chars. Optional fields: license, compatibility (≤500), metadata and allowed-tools. Bodies should stay under 5000 tokens and 500 lines; references/, scripts/ and assets/ load on demand. Claude Code puts only name and description in context (description + when_to_use truncated at 1,536 chars), injects the body as one message via its Skill tool, and has a `paths` glob field for automatic activation on matching files. The agentskills.io client guide lists three activation paths: file-read activation through an existing file or shell tool using a <location> in the catalog; a dedicated activate tool; or user-explicit /skill-name injected by the harness. It also advises lenient parsing, protecting skill content from compaction and deduplicating activations. For cmd_ai, reading via the shell has a concrete trap: Windows PowerShell 5.1 Get-Content decodes BOM-less UTF-8 as the ANSI code page, which corrupts French accents. It would also make every skill read a plan step that needs approval. serde_yaml is deprecated (0.9.34+deprecated) and serde_yml ≤0.0.12 is unsound (RUSTSEC-2025-0068).

**Recommendation:** Adopt the Agent Skills SKILL.md format verbatim, so skills are portable to and from Claude Code. Put a compact <available_skills> catalog (name, description) in the system prompt. Activation without a second tool works by harness interception of a self-command. The system prompt says: 'to load a skill run: cmd_ai skill <name>'. When the single shell tool receives a command whose program is cmd_ai, the app short-circuits it: no shell is spawned, it is auto-approved as read-only, it doesn't count in N/M, and the stripped body is returned as the tool result wrapped in <skill_content name=…>. Also support user-explicit '/<name>' and optionally Claude-style `paths` globs evaluated by the app against cwd (e.g. package.json for the npm skill). Parse frontmatter with a ~50-line hand-written subset parser (key: value, quoted strings, '>' or '|' blocks) instead of a YAML crate.

Sources: https://agentskills.io/specification, https://agentskills.io/client-implementation/adding-skills-support, https://code.claude.com/docs/en/skills, https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1, https://crates.io/api/v1/crates/serde_yaml, https://rustsec.org/advisories/RUSTSEC-2025-0068
#### 11b. Memory format in memory/ (medium)

Claude Code auto memory is a MEMORY.md index plus topic files, loaded into every session up to the first 200 lines or 25KB. CLAUDE.md holds human-written instructions and auto memory holds learnings. Writing memory through the shell has the same Windows PowerShell 5.1 encoding trap: Out-File and '>' create UTF-16LE files, and Set-Content on a new file uses ANSI.

**Recommendation:** memory/MEMORY.md is a one-line-per-entry index ('- [title](file.md) — hook'), injected at startup with a hard cap (e.g. 200 lines / 25KB). memory/<topic>.md files have a minimal frontmatter (name, description, updated) and are loaded on demand through the same intercepted self-command (`cmd_ai memory show <topic>`). Writes also go through an intercepted self-command (`cmd_ai memory add <topic> <text>`), which the app performs in UTF-8 inside the exe directory. The LLM never writes memory files with shell redirection. Show memory writes in the plan in plan mode.

Sources: https://code.claude.com/docs/en/memory, https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1
#### Cross-cutting: Windows child-process output encoding (medium)

Windows console programs writing to a pipe use the OEM code page (e.g. 850 on French installs), not UTF-8, so String::from_utf8 fails or garbles accents. A llama.cpp fix decodes with GetOEMCP and MB_ERR_INVALID_CHARS for this reason. PowerShell's $OutputEncoding governs how PowerShell talks to external programs. Exact behavior per shell and Windows version was not fully verified.

**Recommendation:** Treat child output as bytes. Decode as UTF-8 first; on failure on Windows, decode with the OEM code page via windows-sys MultiByteToWideChar(GetOEMCP()). For PowerShell commands, prepend `[Console]::OutputEncoding=[Text.Encoding]::UTF8;`. Add a CI test that prints 'éàç' from cmd, powershell and pwsh.

Sources: https://newreleases.io/project/github/ggml-org/llama.cpp/release/b10275, https://users.rust-lang.org/t/charsets-problem/30178, https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-5.1

### Decisions
- **How should 'TUI ouvert' render live execution?**
  - Options: ratatui Viewport::Inline + insert_before (scrollback keeps history) | Alternate screen full-screen app | Raw crossterm printing without ratatui
  - Recommended: ratatui Viewport::Inline + insert_before (scrollback keeps history)
  - Why: Executed commands and outputs stay visible after exit without writing to disk (IDEE §3/§4), and the live region stays small. The official ratatui inline example already matches this design. TestBackend + insta make it testable. Use plain-line output for 'TUI fermé' and non-TTY.
- **Which HTTP client?**
  - Options: ureq 3.5 (blocking, rustls/ring) | reqwest 0.13 + tokio | minreq 3.0 / attohttpc 0.31
  - Recommended: ureq 3.5 (blocking, rustls/ring)
  - Why: In the 2026-10 benchmark it is the smallest pure-Rust TLS client (1,928 KiB stripped vs 4,839 KiB for reqwest-tokio), with the fastest first HTTPS. It needs no async runtime, has platform-verifier and Windows registry proxy features, and its reader API maps directly to Ollama's NDJSON stream.
- **Which TLS trust roots?**
  - Options: rustls + PlatformVerifier default, webpki fallback, extra PEM from the stick | rustls + webpki-roots only (ureq default) | native-tls (OpenSSL/SChannel/SecureTransport)
  - Recommended: rustls + PlatformVerifier default, webpki fallback, extra PEM from the stick
  - Why: The OS trust store carries enterprise and TLS-inspection CAs on locked-down machines. The webpki fallback covers bare Linux boxes, and an extra PEM next to the exe keeps the 'everything on the stick' rule. native-tls links the system OpenSSL dynamically on Linux, which breaks portability.
- **Concurrency model?**
  - Options: std threads + std::sync::mpsc single AppEvent channel | tokio runtime | crossbeam-channel + threads
  - Recommended: std threads + std::sync::mpsc single AppEvent channel
  - Why: There are three or four long-lived threads with no high concurrency, and the free tier allows one LLM request at a time. ratatui is not async and its FAQ advises skipping tokio. std mpsc has been crossbeam-based since 1.67, and this adds no dependencies.
- **CLI argument parser?**
  - Options: lexopt 0.3.2 | clap 4.6 (minimal features) | pico-args 0.5.0
  - Recommended: lexopt 0.3.2
  - Why: It adds 37 KiB against 377-574 KiB for clap, is maintained (release Feb 2026) and handles non-UTF-8 args. The flag surface is tiny, so hand-written --help is trivial. pico-args has had no release since 2022.
- **Windows toolchain?**
  - Options: *-pc-windows-msvc with +crt-static | *-pc-windows-gnu (MinGW) | msvc with dynamic CRT
  - Recommended: *-pc-windows-msvc with +crt-static
  - Why: Tier 1, native on windows-2025 and windows-11-arm runners, and +crt-static removes the VCRUNTIME140.dll dependency that would break 'plug the stick and run' on clean machines. aarch64 needs clang for ring.
- **macOS distribution in V1?**
  - Options: Universal binary via lipo + ad-hoc codesign, documented quarantine removal | Separate arm64/x86_64 binaries | Developer ID signing + notarization
  - Recommended: Universal binary via lipo + ad-hoc codesign, documented quarantine removal
  - Why: One file for both Mac architectures keeps the stick layout simple. Re-signing ad hoc after lipo keeps Apple Silicon happy. Notarization needs a paid Developer ID and can come later if Gatekeeper friction proves blocking.
- **How do hooks detect 'a file was modified'?**
  - Options: Before/after-command stat snapshot + idle polling of an explicit watch list | notify 8.2.1 recommended_watcher | notify 9.0 RC
  - Recommended: Before/after-command stat snapshot + idle polling of an explicit watch list
  - Why: Changes in cmd_ai come mostly from commands it runs itself, so a snapshot around each command is deterministic and costs nothing. notify has documented blind spots (NFS, editors, inotify limits) and 9.0 is still an RC. It can come later behind a cargo feature.
- **How does the model load a skill body with only the shell tool?**
  - Options: Harness-intercepted self-command `cmd_ai skill <name>` (no spawn, auto-approved, not counted) | Model reads SKILL.md with cat/Get-Content/type via the shell | App-side automatic injection only (paths globs / slash command)
  - Recommended: Harness-intercepted self-command `cmd_ai skill <name>` (no spawn, auto-approved, not counted)
  - Why: The model still sees only one tool, and the syntax is identical on every OS and shell. It avoids the PowerShell 5.1 ANSI decoding of UTF-8 files, needs no approval in plan mode and leaves the N/M counter alone. App-side `/name` and `paths` activation can be added on top.
- **Light/dark background detection?**
  - Options: terminal-colorsaurus at TUI startup + config.json 'theme' override | Config-only theme | Hand-rolled OSC 11 query
  - Recommended: terminal-colorsaurus at TUI startup + config.json 'theme' override
  - Why: It is maintained (1.0.3), avoids hangs on unsupported terminals, covers conhost and Windows Terminal ≥1.22, and largely reuses dependencies crossterm already pulls. Because body text uses Color::Reset, a wrong guess only affects accents.
- **How is the LLM layer mocked in tests?**
  - Options: ChatBackend trait + FakeBackend fixtures, plus a std TcpListener NDJSON stub | mockito 1.7.2 dev-dependency | httpmock 0.9.0
  - Recommended: ChatBackend trait + FakeBackend fixtures, plus a std TcpListener NDJSON stub
  - Why: No extra dependencies and fast compiles. mockito brings tokio and hyper even if only for dev builds. The stub still exercises the real ureq streaming path end to end.
- **How is SKILL.md frontmatter parsed?**
  - Options: Hand-written subset parser | serde-saphyr / yaml-rust2 | serde_norway (serde_yaml fork)
  - Recommended: Hand-written subset parser
  - Why: Only name, description and a few scalar keys are needed. serde_yaml is deprecated and serde_yml ≤0.0.12 is unsound, and any YAML crate adds size for no benefit. Parse leniently, as agentskills.io recommends.

### Risks
- [medium] Inline-viewport rough edges: CPR query racing stdin (#2640 open), resize behavior (#984 open), and terminal-specific repaint bugs in conhost. — *Mitigation:* Fixed small viewport height, full redraw on Resize, avoid Terminal::clear in the loop, PTY smoke tests on Windows Terminal and conhost, and a --plain flag that falls back to line output.
- [high] Mojibake from Windows child output (OEM code page) and from PowerShell 5.1 file reads and writes (ANSI / UTF-16LE). — *Mitigation:* Byte-level capture with UTF-8-then-OEM decoding, a UTF-8 OutputEncoding preamble for PowerShell, and all skill and memory I/O done app-side through intercepted self-commands. CI test with French accents.
- [medium] Corporate networks: TLS inspection, PAC-only proxies and NTLM-auth proxies are not handled by ureq out of the box. — *Mitigation:* PlatformVerifier roots, extra_ca_file on the stick, config.json proxy override, and the win-system-proxy feature on Windows. Document that PAC and NTLM are unsupported in V1 and show explicit error messages.
- [medium] Unsigned binaries blocked or flagged: macOS Gatekeeper on quarantined files, Windows SmartScreen and heuristic antivirus (worse with UPX). — *Mitigation:* No UPX, ad-hoc signing on macOS with documented `xattr -d com.apple.quarantine`, and release checksums. Consider Developer ID notarization and Authenticode signing later.
- [medium] Runaway or orphaned processes after cancel or a crash, since Child::kill only reaches the direct child and Child has no Drop. — *Mitigation:* Windows Job Object with KILL_ON_JOB_CLOSE, Unix process_group(0) + killpg, always wait() children, and a cancel test in CI.
- [low] Binary size drifts above the 'lightness first' promise; the ~2.5-3.5 MiB estimate is unverified. — *Mitigation:* CI size budget with cargo-bloat --crates, default-features = false everywhere, and dependency review in each spec/plan.
- [low] aarch64 Windows build fails because ring needs clang, and the VS clang component may be missing on the runner. — *Mitigation:* Check for clang in the windows-11-arm job and install the VS LLVM component if missing. Fallback: ship x64 only on Windows ARM, which runs x64 binaries under emulation (unverified for this app).
- [low] Blocking ureq reads cannot be interrupted instantly when the user cancels a slow LLM stream. — *Mitigation:* Set timeout_connect and timeout_recv_body, check the AtomicBool cancel flag between NDJSON lines, and on cancel detach the thread and ignore its later messages.
- [low] Adopting notify 9.x while it is still a release candidate. — *Mitigation:* V1 uses a stat snapshot and polling; add notify behind a feature flag only after 9.0 is stable.

### Gaps in IDEE.md
- §4 layout shows a single `cmd_ai(.exe)`, but one stick serving Windows, Linux and macOS needs several binaries (e.g. bin/windows-x64, bin/windows-arm64, bin/linux-x64-musl, bin/linux-arm64-musl, bin/macos-universal) sharing one config.json, log/, memory/ and skills/. The spec should say how the user, or a tiny launcher script, picks the right one.
- Network on locked-down machines is not covered: no config.json fields for proxy, extra CA bundle (TLS inspection) or request timeouts, and no stated behavior when the network blocks ollama.com.
- No policy on code signing or quarantine: macOS Gatekeeper on unsigned quarantined binaries and Windows SmartScreen/antivirus on unsigned exes directly affect the 'chez quelqu'un, sur un Mac' and library scenarios.
- Read-only or write-protected media: the golden rule forbids falling back to host temp dirs, so the spec should state what happens when log/ or memory/ is not writable (e.g. run without logs and warn).
- Hooks are described only by one example. Event list, config location (config.json vs hooks/), blocking semantics (can a hook veto a command?), timeout and whether hooks count in the N/M progress are undefined.
- The skill 'format défini' is not chosen. Adopting the Agent Skills SKILL.md spec (name ≤64, description ≤1024) would make skills interoperable with Claude Code.
- The memory/ format is undefined, including who writes memory (LLM via commands vs app), what is loaded at startup and size caps.
- The default shell per OS (pwsh vs Windows PowerShell 5.1 vs cmd; bash vs sh vs zsh) and the output-encoding policy on Windows are unspecified.
- Cancellation semantics are missing: Ctrl-C during a running command or LLM stream, killing process trees, and what happens to the remaining plan steps after a failure (stop, skip, ask).
- One-shot ('TUI fermé') output contract is unspecified: plain text vs JSON lines, and process exit codes for scripting.
- The color-science identity has no measurable target: contrast criterion (WCAG 2 AA 4.5:1 and/or APCA Lc), fallback tiers (truecolor/256/16/none) and NO_COLOR handling are not stated.
- Elevation (§3) interacts with the TUI: sudo password prompts need the TTY (the TUI must suspend raw mode or inherit stdio), and Windows UAC elevation opens a separate process whose output cannot simply be piped back. The UX for this is undefined.
- The API key is stored in plain text in config.json on a removable stick, and the spec does not acknowledge the risk if the stick is lost (no env-var override or key-rotation guidance).

## Command execution, privilege elevation, plan/bypass safety, and total portability (USB/zip) for cmd_ai V1

### Claim checks
- **[partially]** Windows 11 has a built-in sudo that cmd_ai can rely on to elevate a command and capture its output.

### Findings
#### Shell inventory and exact invocation per OS (high)

Windows: PowerShell 7 (pwsh.exe, current LTS 7.6 since 2026-03-18, on .NET 10) is not inbox. It installs side by side in $Env:ProgramFiles\PowerShell\7. Windows PowerShell 5.1 (powershell.exe in %windir%\System32\WindowsPowerShell\v1.0) is always present, and PowerShell 2.0 was removed from Windows 11 24H2 in August 2025. cmd.exe is found via %ComSpec%. Use `cmd.exe /d /s /c "<cmd>"`: /d skips the HKLM/HKCU 'Command Processor\AutoRun' commands that would otherwise run host-defined code first, and /s strips only the outer quotes. For PowerShell use `-NoLogo -NoProfile -NonInteractive -Command <single string>`. -Command collapses exit codes to 0/1 unless the script ends with `exit $LASTEXITCODE`, and -NonInteractive turns Read-Host or confirmation prompts into errors instead of hangs. Unix: /bin/sh is dash on Debian/Ubuntu. macOS defaults to zsh but still ships /bin/bash 3.2.57 (GPLv2). zsh -c always reads /etc/zshenv and ~/.zshenv; -f skips the user one. Non-interactive bash sources $BASH_ENV.

**Recommendation:** Probe once at startup, with no extra processes, by looking up these paths: pwsh (PATH, then $Env:ProgramFiles\PowerShell\7\pwsh.exe), powershell.exe, %ComSpec%; on Unix, /bin/bash, then /bin/sh, plus $SHELL for information. Inject the exact shell name and major version into the system prompt, and have the LLM return {shell, command} per step. Spawn children with env_remove for BASH_ENV, ENV and OLLAMA_API_KEY. Windows argv: [pwsh, -NoLogo, -NoProfile, -NonInteractive, -Command, <script + "\nexit $LASTEXITCODE" guard>]. cmd: Command::new(comspec).raw_arg("/d /s /c \"<cmd>\""). Unix: [/bin/bash, -c, <script>] (or zsh -f -c only if the user selects zsh).

Sources: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh?view=powershell-7.5, https://learn.microsoft.com/en-us/powershell/scripting/whats-new/migrating-from-windows-powershell-51-to-powershell-7, https://devblogs.microsoft.com/powershell/announcing-powershell-7-6/, https://support.microsoft.com/help/5065506, https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd, https://doc.rust-lang.org/std/os/windows/process/trait.CommandExt.html, https://wiki.ubuntu.com/DashAsBinSh, https://scriptingosx.com/2019/06/moving-to-zsh/, https://zsh.sourceforge.io/Doc/Release/Files.html, https://man7.org/linux/man-pages/man1/bash.1.html
#### -EncodedCommand vs -Command (medium)

-EncodedCommand takes base64 of UTF-16LE text and avoids nested-quoting problems. Detection rules flag it, though: SigmaHQ 'Suspicious Encoded PowerShell Command Line' (level high) and the RedCanary-derived '-encodedcommand switch' rules. The decoded content still goes through AMSI and script block logging. On library or corporate PCs with EDR, a portable unsigned exe that spawns powershell -e is exactly what malware looks like.

**Recommendation:** Default to -Command with one argument built by Rust std's MSVC-style quoting (no raw_arg for PowerShell). Do not use -EncodedCommand by default. Add a quoting round-trip unit test suite (quotes, $, backticks, braces, non-ASCII) for both pwsh 7.6 and Windows PowerShell 5.1.

Sources: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh?view=powershell-7.5, https://detection.fyi/sigmahq/sigma/windows/process_creation/proc_creation_win_powershell_base64_encoded_cmd, https://detection.fyi/mbabinski/sigma-rules/2024_redcanary_threatdetectionreport/technique_powershell_encoded_command/, https://cyberwarrior76.substack.com/p/decoding-the-chain-a-practitioners
#### Windows output encoding (mojibake on French and other non-US systems) (medium)

The Windows console still defaults to the OEM code page of the system locale, for example 437 (US) or 850 (Western Europe). PowerShell assumes native-command output is in [Console]::OutputEncoding. The usual UTF-8 prelude `[Console]::OutputEncoding=[Text.UTF8Encoding]::new()` fails in ConstrainedLanguage mode, because [Console] and System.Text types are not on the allowed-types list. PowerShell switches to ConstrainedLanguage automatically under AppLocker or WDAC, which is exactly the restricted-library scenario. PowerShell 7 itself writes utf8NoBOM. ConPTY streams are UTF-8, but come wrapped in VT sequences.

**Recommendation:** Treat child output as bytes. Decode UTF-8 first. On Windows, if a chunk is invalid UTF-8, decode it as GetOEMCP() via a small code-page table (or encoding_rs), and never panic. Apply the PowerShell UTF-8 prelude only when $ExecutionContext.SessionState.LanguageMode is FullLanguage, probed once per session. Optionally prefix cmd commands with `chcp 65001>nul &`. Keep a test fixture with French accented file names.

#### Live streaming and capture without hangs (high)

tokio 1.54.x process: pipe stdout and stderr and read both at the same time (two tasks or select!), then wait(). Claude Code's issue tracker shows the two classic failure modes: an inherited stdin makes any child that reads stdin hang forever, and with no controlling TTY, sudo prints nothing. PowerShell honors TERM=dumb (SupportsVirtualTerminal=false) and NO_COLOR (plain-text rendering), which keeps captured output clean.

**Recommendation:** stdin = Stdio::null() for every agent-run command. Set PAGER=cat, GIT_PAGER=cat, NO_COLOR=1 and TERM=dumb in the child env. Read raw byte chunks so that \r progress output is handled, display them live in the TUI, and write the full output to log/. Send the LLM only a capped excerpt (e.g. first 4 KB + last 8 KB + 'N bytes truncated') plus the exit code and duration.

#### Timeouts and killing whole process trees (high)

tokio's kill_on_drop kills only the direct child and does not reap it. Windows: put each command in a Job Object. TerminateJobObject kills every member, and JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE kills all members when the last handle closes, including when cmd_ai crashes. A child leaves the job only through CREATE_BREAKAWAY_FROM_JOB plus JOB_OBJECT_LIMIT_BREAKAWAY_OK or SILENT_BREAKAWAY_OK. Unix: Command::process_group(0) (std since 1.64) then killpg. A descendant calling setsid escapes the group (processkit docs). process-wrap 10.0.1 (watchexec, MIT/Apache-2.0, MSRV 1.87, `tokio1` feature) wraps JobObject, ProcessGroup, ProcessSession, KillOnDrop and CreationFlags, and its README warns that wrapper order matters.

**Recommendation:** Use process-wrap with tokio1: JobObject + KillOnDrop + CreationFlags(CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP) on Windows; ProcessGroup::leader() on Unix, not ProcessSession, so sudo can still see the controlling TTY. Default timeout per step: 120 s, configurable in config.json. On Esc, cancel or time out: SIGTERM to the group, a 3 s grace period, then SIGKILL or TerminateJobObject, then report 'killed (timeout)' to the LLM.

#### GUI launches ('open YouTube') and their interaction with tree-kill (medium)

Windows: `start "" "https://www.youtube.com"` in cmd, because the first quoted argument is the window title. URLs and documents open through their file association. In PowerShell, Start-Process '<url>' works and the started process runs on independently. macOS: `open <url>` (-a picks the app, -W waits). Linux: `xdg-open <url>` may block for a long time when the handler is a terminal app; exit codes are 1=syntax, 2=file missing, 3=tool missing, 4=action failed. On non-Windows, Start-Process keeps the child attached to the shell (nohup needed). If cmd_ai kills the job or process group on timeout or exit, a browser it cold-started can be killed with it.

**Recommendation:** Mark launcher steps (start, Start-Process, Invoke-Item, open, xdg-open) as kind=gui-launch. Run them detached: on Windows, spawn with CREATE_BREAKAWAY_FROM_JOB in a job that allows breakaway; on Unix, setsid + nohup semantics and a short 10 s timeout. Treat 'process exited 0' as success, and don't wait for the app itself.

#### Interactive commands: a PTY or not (high)

ConPTY needs Windows 10 1809+, and portable-pty 0.9.0 (wezterm, 2025-02-11, 15 normal dependencies including winapi and nix) would add VT parsing work. Apple's TN2065 shows the alternative: run tools in non-TTY mode (e.g. `top -l1`). Simple executors such as shell-gpt and aichat run the command in the user's own terminal after an [E]xecute/[D]escribe/[A]bort prompt, so interactive tools just work. The Ratatui 'spawn vim' recipe shows how: leave the alternate screen, disable raw mode, run with inherited stdio, then restore.

**Recommendation:** V1 has no PTY. Default is captured and non-interactive (stdin null). Add an explicit 'handover' step kind (LLM flag interactive=true, or the user presses a key): suspend the TUI per the Ratatui recipe, run with inherited stdio and no capture (log only command, exit code and duration), then resume. Reconsider portable-pty in V2 only if real use shows a need.

#### Detecting the current privilege level and when a step needs elevation (high)

Windows: GetTokenInformation returns TokenElevation and TokenElevationType. Default means no linked token (a standard user, or UAC off); Limited means a split-token admin who can elevate through a consent prompt; Full means already elevated. CreateProcess of a requireAdministrator binary fails with ERROR_ELEVATION_REQUIRED (740), and many admin operations fail with 'Access is denied'. Unix: geteuid()==0. `sudo -n true` never prompts and fails if a password would be needed. sudoers timestamp_type=tty by default, falling back to ppid with no terminal, with a 5-minute timeout.

**Recommendation:** At startup, compute a privilege profile and show it in the status bar: windows {elevated, elevation_type} or unix {euid0, sudo_cached via `sudo -n true`, sudo present}. Ask the LLM for a needs_admin boolean on every step. Also classify failures after the fact (exit 740, 'Access is denied', EACCES/EPERM, 'Permission denied', 'Operation not permitted', 'are you root') and propose an elevated retry instead of retrying blindly. If elevation_type is Default and the user is not admin (typical in a library), tell the LLM elevation is impossible so it plans a user-level alternative.

#### Windows elevation strategies (high)

(1) Start-Process -Verb RunAs or ShellExecuteExW 'runas' opens a separate window with no capture. The crate privesc 1.2.0 (2025-12-25) states it cannot capture output on Windows. (2) Inbox sudo: off by default, and enabling it needs admin. (3) gsudo portable captures output, but it is a third-party .NET 9 exe with a credential-cache risk. (4) Administrator protection, rolling out since KB5120998 (Aug 2026): off by default, but on by default in Windows security baselines from the October 2026 update. **Recommendation:** V1: when a plan contains needs_admin steps and the session is not elevated, offer 'Restart cmd_ai as administrator'. Elevate per step only in V2, through a cmd_ai.exe --elevated-runner helper that streams over an ACL-restricted named pipe. Do not depend on inbox sudo or gsudo. When admin protection is on, warn that user-profile paths resolve to the hidden admin profile.

#### Unix and macOS elevation inside a TUI (medium)

sudo reads the password from /dev/tty, so a piped child with no TTY can't be answered. Claude Code's own `!` mode fails silently on sudo prompts. sudo -S reads the password from stdin, which would mean cmd_ai handles the user's password. -A/SUDO_ASKPASS is documented in sudo-rs, though a Ubuntu 25.10 thread reported that Cockpit broke because sudo-rs lacked --askpass. macOS also has `osascript -e 'do shell script "…" with administrator privileges'`: it shows a GUI password dialog, runs /bin/sh as root, returns stdout (CR line endings unless `without altering line endings`), turns stderr plus a non-zero status into an AppleScript error, has no TTY, and caches authentication for 5 minutes per script. Claude Code refuses bypass mode as root.

**Recommendation:** Default flow: a handover step runs `sudo -v` with inherited TTY, so the password goes straight from the user to sudo. Then run the admin steps captured as `sudo -n <cmd>` within the 5-minute window, with children in the same session (process group, no setsid) so the tty timestamp record applies. If `sudo -n` fails, go back to handover. Never collect passwords in the TUI and never use -S. macOS fallback when no TTY is usable: osascript 'with administrator privileges'. Refuse bypass mode when euid==0, unless --allow-root is given.

#### Plan mode and bypass mode in existing agents (high)

Claude Code: plan mode allows read-only exploration and blocks edits until a plan is approved ('Yes, auto mode/auto-accept', 'Yes, manually approve edits', 'No, keep planning'). In bypassPermissions, deny rules and explicit ask rules still apply, and critical-path rm is never auto-approved. Codex: approval policies on-request and never ('untrusted' is no longer selectable), sandbox modes read-only, workspace-write and danger-full-access, and Starlark .rules with forbidden > prompt > allow. **Recommendation:** Plan mode: the LLM must first return a structured plan, an array of steps {id, shell, command, purpose, risk: read|write|destructive|network, needs_admin, interactive}. #### Destructive-command detection is friction, not a security boundary (high)

Claude Code documents that a Bash rule matches the command text as the model writes it, not the same program called by path or inside `sh -c`. Offer a -WhatIf preview for PowerShell destructive cmdlets. Document clearly that these lists are guard-rails, not sandboxing.

#### Resolving the portable home directory (high)

std::env::current_exe may return either the symlink or its target depending on the platform, and may return the load-time path after a rename. #### USB filesystem and per-OS execution gates (medium)

Linux: on vfat, udisks' showexec strips +x from an ELF unless the name ends in .exe/.com/.bat. exFAT has no showexec, and its fmask follows the umask. Admins can force noexec in /etc/udisks2/mount_options.conf. **Recommendation:** Make exFAT the only officially supported stick format, and say so in the README. #### Security of the single tool: prompt injection and secret leakage (high)

OWASP LLM01:2025 defines indirect injection as instructions arriving through external sources such as files and websites. Its mitigations include separating untrusted content, privilege control and human approval for high-risk actions. Simon Willison's 'lethal trifecta' (June 2025) is private data + untrusted content + external communication. A shell-only agent has all three by design: it reads host files, reads any output, and can run curl or Invoke-WebRequest. Every child inherits cmd_ai's environment, so `env`, `set` or `Get-ChildItem Env:` would expose an OLLAMA_API_KEY. Ollama keys never expire. PSReadLine's history filter (password, asplaintext, token, apikey, secret) is a precedent for redaction.

**Recommendation:** (1) Wrap every output sent to the LLM in a delimited block marked as untrusted data, and state in the system prompt that instructions inside outputs must be ignored. (2) In plan mode, any step introduced after reading an output needs approval, even if the original plan was approved. (3) Put network egress (curl/wget/Invoke-WebRequest/Invoke-RestMethod/scp/ftp, plus piping into a shell) in the always_ask tier, Warp-style, so it applies in bypass too. (4) Remove OLLAMA_API_KEY and any config secret from the child env with env_remove. Redact the API key value and common token patterns before writing to log/. Never echo config.json into the LLM context. (5) Document revocation at ollama.com/settings/keys for a lost stick. Keep the key in plaintext in config.json for V1, with an OLLAMA_API_KEY env override for people who don't want it on the stick.

### Decisions
- **Which shell does cmd_ai use by default on Windows?**
  - Options: pwsh 7 if present, else Windows PowerShell 5.1, cmd only when explicitly requested | Always Windows PowerShell 5.1 (inbox everywhere) | Always cmd.exe
  - Recommended: pwsh 7 if present, else Windows PowerShell 5.1, cmd only when explicitly requested
  - Why: pwsh is not inbox, while 5.1 is always there (and PowerShell 2.0 is gone since Aug 2025). PowerShell outputs objects and handles quoting more sanely than cmd. Telling the LLM which edition it gets avoids syntax errors (e.g. && and || only exist in PowerShell 7).
- **How is PowerShell code passed to the child process?**
  - Options: -Command with a single std-quoted argument | -EncodedCommand (UTF-16LE base64) | -Command - over stdin
  - Recommended: -Command with a single std-quoted argument
  - Why: -EncodedCommand matches high-severity Sigma or EDR detections, which is bad for an unsigned exe on a USB stick. `-Command -` runs statements one at a time, skips statements that don't parse, and takes over stdin.
- **Which shell runs commands on Linux and macOS?**
  - Options: /bin/bash -c (fallback /bin/sh) with BASH_ENV/ENV removed | The user's $SHELL | Always /bin/sh
  - Recommended: /bin/bash -c (fallback /bin/sh) with BASH_ENV/ENV removed
  - Why: LLMs write bash dialect most reliably. /bin/sh is dash on Debian/Ubuntu, zsh -c reads ~/.zshenv from the host, and macOS bash 3.2 is predictable as long as the version is stated in the prompt.
- **Does V1 need a pseudo-terminal?**
  - Options: No PTY: stdin null plus an explicit TTY-handover step | portable-pty for every command | ConPTY on Windows only
  - Recommended: No PTY: stdin null plus an explicit TTY-handover step
  - Why: It keeps the binary lighter (portable-pty brings about 15 dependencies and VT parsing) and LLM output cleaner. Handover covers sudo passwords, ssh and editors with no extra code beyond the Ratatui suspend recipe.
- **How does cmd_ai elevate on Windows?**
  - Options: Relaunch the whole cmd_ai session elevated (ShellExecuteExW runas on current_exe, --resume) | Per-step elevated helper streaming over a named pipe | Use inbox sudo when enabled | Bundle gsudo on the stick
  - Recommended: Relaunch the whole cmd_ai session elevated (ShellExecuteExW runas on current_exe, --resume)
  - Why: It is the only option that captures every elevated command's output with no third-party binary and no reliance on a setting that is off by default. A per-step helper is better UX but more code and attack surface, so it fits V2.
- **How does cmd_ai elevate on Linux and macOS?**
  - Options: TTY handover for `sudo -v`, then captured `sudo -n` within the cache window | sudo -S with the password typed into the TUI | SUDO_ASKPASS helper | macOS osascript for every admin step
  - Recommended: TTY handover for `sudo -v`, then captured `sudo -n` within the cache window
  - Why: The password never passes through cmd_ai. It works with sudo.ws and sudo-rs, which documents -n and -v. osascript stays a macOS fallback for when no TTY is usable.
- **At what granularity are steps approved in plan mode?**
  - Options: Hybrid: approve the whole plan once; re-confirm destructive, admin, and post-replan steps | Approve each step | Approve the whole plan only
  - Recommended: Hybrid: approve the whole plan once; re-confirm destructive, admin, and post-replan steps
  - Why: It matches the IDEE goal ('on regarde, on dit OK, ça exécute') while closing the injection path where an output rewrites the plan. Claude Code and Codex both keep extra gates for the riskiest actions.
- **Does a deny-list still apply in bypass mode?**
  - Options: Yes: an always_ask tier that prompts even in bypass, plus a never tier changeable only in config.json | No: bypass means zero prompts | Hard-block everything on the list
  - Recommended: Yes: an always_ask tier that prompts even in bypass, plus a never tier changeable only in config.json
  - Why: This matches how Claude Code (deny and ask rules survive bypass), OpenCode (--auto keeps deny) and Warp (the denylist beats full autonomy) handle it. Hard-blocking everything would stop legitimate tasks such as formatting a USB stick.
- **What happens to GUI apps cmd_ai launches when a step times out or cmd_ai exits?**
  - Options: Detected launchers run detached (breakaway from the job, setsid on Unix) | Same job or process group as every other step
  - Recommended: Detected launchers run detached (breakaway from the job, setsid on Unix)
  - Why: Otherwise 'open YouTube' can kill the browser on timeout or exit, because the job and process-group kill reaches every member.
- **What happens when log/ and memory/ cannot be written?**
  - Options: Ephemeral in-RAM mode with a visible banner; host dirs only via explicit --state-dir | Silently fall back to the host temp dir | Refuse to start
  - Recommended: Ephemeral in-RAM mode with a visible banner; host dirs only via explicit --state-dir
  - Why: It keeps the golden rule ('rien sur l'hôte') and still lets the tool work in libraries that deny writes to removable disks.
- **Which USB filesystem is officially supported?**
  - Options: exFAT | FAT32 | NTFS
  - Recommended: exFAT
  - Why: udisks mounts vfat with showexec, which blocks the Linux ELF. exFAT is read/write on all three OSes, has no showexec default, and its fmask follows the umask.
- **Should releases be code-signed?**
  - Options: V1 unsigned with documented workarounds; plan Windows signing and Apple notarization before 1.0 | Sign and notarize from the first release | Never sign
  - Recommended: V1 unsigned with documented workarounds; plan Windows signing and Apple notarization before 1.0
  - Why: Signing costs money and paperwork (Artifact Signing limits individuals to USA/Canada). Without it, SAC and Gatekeeper block the 'plug in at someone's house' scenario, so it has to be on the roadmap.
- **How is the Ollama API key stored and protected?**
  - Options: Plaintext in config.json + OLLAMA_API_KEY env override + env scrubbing for children + log redaction | Passphrase-encrypted key in config.json | OS keychain
  - Recommended: Plaintext in config.json + OLLAMA_API_KEY env override + env scrubbing for children + log redaction
  - Why: An OS keychain breaks portability and the no-host rule. Encryption adds a prompt at every launch, so it can be optional in V2. Scrubbing and redaction close the realistic leak paths, and revocation covers a lost stick since keys never expire.

### Risks
- [high] In the library scenario the binary never starts: Smart App Control, AppLocker default rules, or the GPO 'Removable Disks: Deny execute access' block an unsigned exe on removable media. — *Mitigation:* Document it honestly in IDEE and the docs. Add code signing to the roadmap. The launcher scripts cannot work around a policy, so do not promise library support without signing.
- [high] Prompt injection through command output (a file or web page telling the agent to run commands) leads to destructive or data-exfiltration commands, especially in bypass mode. — *Mitigation:* Mark outputs as untrusted. Re-approve any step added after replanning. Keep network egress and destructive commands in an always_ask tier that applies in bypass.
- [high] The API key leaks through child environment dumps, logs on the stick, or a lost stick; Ollama keys never expire. — *Mitigation:* env_remove secrets for every child. Redact before writing to log/. Document revocation at ollama.com/settings/keys. Offer the env-var option.
- [medium] Output is garbled on non-English Windows (OEM code page 850 in France), and the UTF-8 prelude fails under ConstrainedLanguage mode. — *Mitigation:* Decode bytes as UTF-8 first with an OEM fallback. Probe the language mode before using .NET-based preludes.
- [medium] Commands hang on stdin, pagers or sudo password prompts when there is no TTY. — *Mitigation:* stdin null, PAGER=cat and GIT_PAGER=cat, `sudo -n`, a per-step timeout with tree kill, and an explicit handover mode.
- [medium] The Linux ELF cannot be run from a FAT32 stick (showexec). — *Mitigation:* Support exFAT officially. The launcher detects the problem and prints the fix.
- [medium] EDR or AV flags cmd_ai because an unsigned binary spawns PowerShell with encoded commands. — *Mitigation:* Never use -EncodedCommand by default. Use plain -Command and a stable argv shape.
- [medium] Elevated steps behave differently under Administrator protection (hidden admin profile, no network drives, a Windows Hello prompt for each elevation). — *Mitigation:* Detect elevation through the relaunch path. Warn the LLM that per-user paths differ once elevated. Keep elevated sessions short.
- [medium] Browsers or apps that cmd_ai opens are killed when a step times out or cmd_ai exits. — *Mitigation:* Classify launcher commands and run them detached (job breakaway, setsid).
- [medium] On macOS, the TCC prompt for removable volumes or the Gatekeeper block stops the first run; the TCC grant is stored on the host. — *Mitigation:* Document the first-run steps. Long term, notarize the binary.
- [low] Users expect 'zero trace', but the OS records execution (Prefetch, Amcache, SRUM, USBSTOR, audit logs). — *Mitigation:* Reword the golden rule as 'cmd_ai stores nothing', and document the uncontrollable artifacts.
- [medium] Destructive-command regexes are bypassed through wrappers (sh -c, Invoke-Expression, variables) and give a false sense of security. — *Mitigation:* Combine the regexes with the LLM-declared risk and human approval. Say in the docs that these lists are guard-rails, not a sandbox.

### Gaps in IDEE.md
- The golden rule 'rien ne se stocke sur la machine hôte' needs a precise scope: what cmd_ai writes versus OS-level execution artifacts (Prefetch, Amcache, SRUM, USBSTOR, TCC, audit logs), which it cannot control.
- No behavior is defined for read-only or write-protected media, where log/ and memory/ cannot be written.
- No default shell per OS, no rule for how the LLM learns which shell and version it is targeting, and no fallback order (pwsh / powershell 5.1 / cmd; bash / sh / zsh).
- Execution semantics are missing: per-step timeout, cancel key, process-tree kill, output size cap sent to the LLM, and handling of commands that need a TTY or stdin.
- Windows elevation UX is unspecified: Windows cannot capture output from a separate UAC window, so a choice is needed between relaunching the session elevated, a per-step helper, or inbox sudo (off by default). Administrator protection's profile separation is also not covered.
- Unix elevation is unspecified: how the sudo password reaches sudo without cmd_ai touching it (TTY handover), and how sudo -n / timestamp caching are used.
- Plan mode lacks rules for replanning after outputs (re-approval and plan diff), per-step versus whole-plan approval, and whether read-only discovery commands may run before the plan.
- Bypass mode does not say whether a deny or always-ask list still applies; existing agents keep one.
- The 'plug in at the library or a stranger's Mac' scenario does not mention Smart App Control, AppLocker, removable-media execute policies, Gatekeeper or notarization, or the macOS TCC removable-volume prompt; it may not be achievable without code signing.
- The supported USB filesystem is not specified; FAT32 breaks the Linux binary under udisks showexec.
- No API key protection: keys never expire, there is no redaction in log/, no scrubbing from child environments, and no revocation procedure for a lost stick.
- No prompt-injection threat model, even though a shell-only agent combines private data, untrusted content and external communication.
- The release matrix is unspecified: which OS/arch binaries ship (x86_64/aarch64, macOS universal2), their names, and launcher scripts.
- No policy for running when cmd_ai is already root or admin (Claude Code refuses bypass mode as root).

#### GitHub Pages availability depends on repo visibility (high)

GitHub Pages is available for public repositories on GitHub Free, and for private repositories only on Pro, Team or Enterprise. The free arm64 runners (ubuntu-24.04-arm, windows-11-arm) are also free only for public repos. A project site's URL is <owner>.github.io/<repositoryname>, with one Pages site per repo.

**Recommendation:** Decide visibility before writing pages.yml: a public repo gets free Pages, unlimited standard runner minutes and arm64 builds. If it must stay private, budget for GitHub Pro or host the docs elsewhere. Note that the user's other private projects use Vercel, but IDEE requires GitHub Pages.

Sources: https://help.github.com/articles/what-is-github-pages, https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages, https://docs.github.com/en/actions/reference/runners/github-hosted-runners

### Decisions
- **How should the closing recap at the end of every AI run be enforced?**
  - Options: CLAUDE.md instruction only | Claude Code Stop hook (command) that blocks when the marker heading is missing and injects the computed Spec Kit state, plus the format in CLAUDE.md | Prompt-type Stop hook asking a model whether the recap is present
  - Recommended: Claude Code Stop hook (command) that blocks when the marker heading is missing and injects the computed Spec Kit state, plus the format in CLAUDE.md
  - Why: The docs call CLAUDE.md context, not enforcement. A command Stop hook reads last_assistant_message, is deterministic, costs no tokens when the recap is present, and is loop-safe through stop_hook_active and the 8-continuation cap. Injecting the computed state means the recap reflects disk reality rather than Claude's memory.
- **Should the recap be required on every turn or only on working turns?**
  - Options: Every turn (IDEE wording: 'à la fin de chaque exécution') | Only when the turn changed files (git status --porcelain non-empty)
  - Recommended: Every turn (IDEE wording: 'à la fin de chaque exécution')
  - Why: This matches IDEE literally and needs no git heuristics. The hook passes immediately when the marker is present, so the cost is a short checklist. Switch to the file-change variant only if it proves noisy in practice.
- **Which Spec Kit script variant should be used?**
  - Options: --script ps | --script sh | --script py
  - Recommended: --script ps
  - Why: It is the default on Windows, needs no WSL, and the development machine is Windows. py is newer and cross-platform, but its maturity is less proven. Switching later is possible with `specify integration upgrade claude --script py`.
- **Should Claude be allowed to auto-invoke Spec Kit skills?**
  - Options: Default (model-invocable) | --no-model-invocation (only when the user types /speckit-<cmd>)
  - Recommended: --no-model-invocation (only when the user types /speckit-<cmd>)
  - Why: Phases such as /speckit-implement or /speckit-constitution change governance and code, so a human should start each phase explicitly. Extension skills stay invocable. The option is stored and re-applied on upgrade.
- **Should the Spec Kit git extension (feature branches, auto-commit) be installed?**
  - Options: No (V1): specs/NNN-* numbering only, work on main | Yes with auto_commit disabled (branches 001-xxx per feature)
  - Recommended: No (V1): specs/NNN-* numbering only, work on main
  - Why: It is opt-in since recent releases, and Spec Kit works fully without it. Lightness comes first, and auto-commit would conflict with the user's habit of reviewing commit content before committing. It can be added later with `specify extension add git` if a PR-per-feature flow is wanted.
- **How should test-first be guaranteed in generated tasks?**
  - Options: Constitution article only | Constitution article + .specify/templates/overrides/spec-template.md and tasks-template.md | Full custom preset
  - Recommended: Constitution article + .specify/templates/overrides/spec-template.md and tasks-template.md
  - Why: /speckit-tasks generates tests only when the spec asks for them, so a constitution article alone is not enough. Project-local overrides have the highest priority, survive upgrades, and are lighter than a preset.
- **How should Fumadocs reach doc/ at the repo root?**
  - Options: defineDocs({ dir: '../doc' }) + turbopack.root = repo root | Copy doc/ into doc-site/content at build time | Move the Next app to the repo root
  - Recommended: defineDocs({ dir: '../doc' }) + turbopack.root = repo root
  - Why: It meets IDEE's 'no duplication' rule and keeps doc-site/ separate. The known '../' bug was fixed on 2026-10-02 (fumadocs-mdx 15.4.10 is current). Copying content would create a second copy, and moving the app breaks the tree IDEE defines.
- **Where should meta.json ordering files live?**
  - Options: Single doc/meta.json (plus per-folder meta.json only if needed) | No meta.json (alphabetical order) | Numeric filename prefixes
  - Recommended: Single doc/meta.json (plus per-folder meta.json only if needed)
  - Why: Fumadocs only reads meta.json from inside the content directory. It is navigation metadata, not duplicated content. Numeric prefixes would leak into URLs and slugs, which hurts SEO.
- **How should bug fiches appear in the documentation?**
  - Options: Second Fumadocs collection on ../bug (rendered under /bugs) | Links from doc/ to GitHub blob URLs
  - Recommended: Second Fumadocs collection on ../bug (rendered under /bugs)
  - Why: This shows the fiches in the docs with zero duplication and uses the same mechanism as doc/. It is supported by declaring another collection with its own loader. If bugs should not be public or indexed, keep the GitHub links instead and add `robots: { index: false }` for /bugs.
- **How should Google Search Console verification be done?**
  - Options: HTML tag via Next metadata.verification.google on a URL-prefix property | HTML file in doc-site/public/ | DNS (Domain property) | Custom subdomain + DNS
  - Recommended: HTML tag via Next metadata.verification.google on a URL-prefix property
  - Why: The tag lives in code, is re-checked periodically, and works for https://<owner>.github.io/cmd_ai/. DNS is impossible on github.io. A custom subdomain is the only route to a Domain property and a working robots.txt, but it adds DNS management.
- **Release tooling?**
  - Options: Hand-written release.yml + gh release create | cargo-dist (dist init) with installers = [] | softprops/action-gh-release
  - Recommended: Hand-written release.yml + gh release create
  - Why: IDEE §4 needs a specific zip layout (a cmd_ai/ folder with exe, config.example.json and empty log/, memory/, skills/), a universal macOS binary and no host installers. A short YAML file does this transparently, uses only the preinstalled gh CLI, and keeps 'GitHub Actions in YAML' literal. cargo-dist's strengths (installers, homebrew) don't apply here.
- **How should bug state stay in sync with GitHub issues?**
  - Options: Manual fiche status + 'Fixes #N' commits + read-only bug-lint workflow | Bot workflow that writes bug/ files on issue events | Spec Kit bug extension
  - Recommended: Manual fiche status + 'Fixes #N' commits + read-only bug-lint workflow
  - Why: The bug/ fiche stays the human-written source of truth, and closing keywords close issues on merge. A read-only check catches drift without CI committing to the repo. The Spec Kit bug extension uses three files per bug in .specify/bugs/, which contradicts IDEE.
- **Should the Spec Kit agent-context extension manage a block in CLAUDE.md?**
  - Options: No: CLAUDE.md hand-written, live state computed by hooks | Yes: let it maintain <!-- SPECKIT START/END --> pointing at the latest plan.md
  - Recommended: No: CLAUDE.md hand-written, live state computed by hooks
  - Why: The block only points at the most recent plan.md, adds a PyYAML dependency and churns CLAUDE.md diffs. The SessionStart and Stop status script already gives a richer, always-current view.

### Risks
- [high] D:\ is the enclosing git repository: commits or pushes from D:\cmd_ai\cmd_ia would land in a repo containing the whole drive, and Claude Code or tools would see hundreds of unrelated untracked folders. — *Mitigation:* Clone the new GitHub repo or run `git init` in the project folder before `specify init`. Check that `git rev-parse --show-toplevel` prints the project path. Optionally set GIT_CEILING_DIRECTORIES.
- [medium] Spec Kit releases churn quickly (four minor/patch releases in October 2026, command spellings changed, taskstoissues deprecated, git made opt-in), so docs, CLAUDE.md and habits go stale. — *Mitigation:* Pin `specify-cli==1.2.4`. Upgrade on purpose with `specify integration upgrade claude` and review the diff. Keep command names in one place (CLAUDE.md) and re-read the release notes before each upgrade.
- [medium] Spec Kit event handlers (enabled by default) write to .claude/settings.json, the same file as the custom Stop and SessionStart hooks. An upgrade could rewrite or reorder them; merge behavior was not verified. — *Mitigation:* Diff .claude/settings.json after every init or upgrade. If no extension needs events, disable them with the integration option `--events false`. Keep the hook scripts in .claude/hooks/ so restoring the settings entries is trivial.
- [high] Test tasks are optional by default in /speckit-tasks, so IDEE's 'tests are part of implementation' rule can silently disappear. — *Mitigation:* Add a Test-First NON-NEGOTIABLE article, the spec-template and tasks-template overrides in .specify/templates/overrides/, and a CI matrix running `cargo test --locked` on 3 OSes. /speckit-analyze flags a violated MUST as CRITICAL.
- [medium] Fumadocs outside-dir collections are not officially documented; issue #3623 broke '../' paths in 15.2.1-15.4.5. — *Mitigation:* Use fumadocs-mdx >=15.4.10 with a lockfile. In pages.yml, fail the build if the docs page count is 0 or a known page is missing. Watch Fumadocs releases before bumping.
- [medium] The create-fumadocs-app template's defaults (LLM integration proxy.ts and rewrites, dynamic OG image routes) are unsupported by `output: 'export'` and fail the build or 404 on Pages. — *Mitigation:* Remove proxy.ts and rewrites. Keep the llms.txt routes with revalidate=false only if wanted. Replace per-page OG generation with a static opengraph-image.png.
- [medium] basePath pitfalls on a project page: search index fetched from /search-index.json without the /cmd_ai prefix (404), images without the prefix, and the root RSC payload 404 with trailingSlash false (Next #73427). — *Mitigation:* Set trailingSlash: true and pass basePath explicitly to useStaticSearch `from` and to image src. Smoke-test the deployed site (home, a deep page, search, client navigation) after the first deploy.
- [low] Turbopack root set to the repo root makes `next dev` watch the Rust target/ directory, which can be large. — *Mitigation:* This only affects local dev, since CI builds once. If dev gets slow, move Cargo's target-dir outside the repo or exclude it. Don't widen the root beyond the repo.
- [low] robots.txt and the Sitemap: directive cannot be set for <owner>.github.io/cmd_ai, so crawlers rely on the owner-level robots.txt. — *Mitigation:* Submit sitemap.xml by hand in Search Console and use per-page `robots` metadata. Use a custom subdomain if full control is needed.
- [medium] Unsigned binaries: macOS Gatekeeper and Windows SmartScreen may block or warn on first run on a stranger's machine, and exec bits may not survive FAT or exFAT USB sticks. Behavior on removable media was not verified in this research. — *Mitigation:* Document first-run steps in doc/. Test the release zip on a real Mac and Windows PC from a USB stick before V1. Consider code signing and notarization as a later decision; it is out of current scope.
- [low] Runner churn: macos-14 retires 2026-11-02 and Intel macOS runners end in 2027 (x86_64-apple-darwin is already Tier 2). — *Mitigation:* Use macos-latest (arm64) and cross-compile x86_64-apple-darwin plus lipo for a universal binary, rather than depending on Intel runners.
- [medium] A private repo on GitHub Free cannot publish Pages, which blocks the documentation requirement. — *Mitigation:* Choose a public repo, which also gives free arm64 runners, or budget for GitHub Pro.
- [high] Secrets: config.json holds the Ollama API key and lives next to the binary; a dev copy could be committed or attached to bug reports and logs. — *Mitigation:* Gitignore config.json, /log and /memory. Ship only config.example.json. The issue form warns against pasting keys, and the app should redact the key in log/.

### Gaps in IDEE.md
- IDEE §6 names Spec Kit commands /specify, /plan, /tasks, /implement. With the Claude integration in Spec Kit 1.2.x they are /speckit-specify, /speckit-plan, /speckit-tasks, /speckit-implement. IDEE also does not say whether /speckit-clarify, /speckit-checklist, /speckit-analyze and the new /speckit-converge are part of the workflow.
- The closing-recap stage list (constitution, spécifié, planifié, tâches, implémenté) has no 'clarifié' or 'convergé' stage, although Spec Kit produces both.
- GitHub owner, repository name and visibility are not stated. They determine the Pages URL (<owner>.github.io/cmd_ai), basePath, the Search Console property and whether Pages is free (private repos need Pro).
- The project folder D:\cmd_ai\cmd_ia is not its own git repository (the enclosing repo is D:\); IDEE assumes a standalone GitHub repo.
- The portable tree in §4 shows a single `cmd_ai(.exe)`, but the scenarios (a Mac at a friend's, a library PC) imply one USB stick for several OSes. The Linux and macOS binaries would both be named `cmd_ai`. IDEE needs to choose per-OS zips or a multi-OS folder with distinct binary names (e.g. cmd_ai.exe, cmd_ai-macos, cmd_ai-linux) sharing config/log/memory/skills.
- No rule for config.json vs a shipped example: releases should ship config.example.json so upgrades never overwrite the user's API key, and config.json must be gitignored.
- Release versioning (SemVer tags vX.Y.Z), CHANGELOG and licence are not defined; they affect release.yml, archive contents and the docs.
- The bug fiche format is not defined: ID scheme (issue number vs BUG-NNN), allowed states, required sections, and whether every bug needs a regression test.
- Documentation language is implied French but not stated (html lang, og:locale, search stemmer, UI translations), and it is not said whether bug fiches should be public or indexed on the doc site.
- IDEE says CLAUDE.md tells 'où on en est', but live state written into CLAUDE.md goes stale. It should specify that state is computed (hook or script) while CLAUDE.md holds pointers.
- No measurable 'lightness' budgets (binary size, startup time, dependency count), so a constitution principle on lightness cannot be checked until numbers exist.
- Whether the doc site uses a custom (sub)domain or the github.io path is open; it changes SEO capabilities (robots.txt, DNS verification) and the basePath setup.
